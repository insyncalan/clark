# Design note: Windows host-side behaviour in the container (v1.1, item 625)

Status: part of item 625, not the whole. Built: `src/clark/host_folders.py` and `tests/test_host_folders.py`, and one call of `to_container`
from the pasted client folder in `publish_flow.py` (`client_folder`, action paste; `tests/test_host_folders_route.py`). Everything
else under "Wiring" below is not built, so this change does not close item 625. `server.py` and `platform.py` are not touched; wiring most
of the rest does not need `server.py` (see "Not built").

## The problem in plain words

On the Windows route clark runs in Docker. From inside, it sees Linux and only the folders Docker shares in. It cannot open a
Windows dialog, open a file, reveal a file in Explorer or open a browser. So three things change: the folders Settings keeps
(backup folder, client folder, local files folder; ask clark source folders are off on Windows) are typed as Windows paths and must
be folders that were shared in; a saved file is named in words, in Windows form, because it cannot be revealed; and the To client copy
goes only to a shared client folder.

## What the spike builds (`host_folders.py`, pure, no disk)

- The Windows compose file shares up to three folders, each at a fixed place: `/shares/client`, `/shares/backup`, `/shares/files`
  (client folder, backup copy folder, the local folder for published and exported files). It names each one's Windows path in
  `CLARK_SHARE_CLIENT`, `CLARK_SHARE_BACKUP`, `CLARK_SHARE_FILES`, and sets `CLARK_HOST=windows` (item 629). The data folder stays a named
  volume at `/data` (item 623 answer 1 and item 622); no share is ever the data folder, and the three mount points are all under `/shares`.
- `to_container(slot, typed, environ)`: a typed `C:\...` or `C:/...` path inside that slot's shared folder (letter case ignored)
  gives the container path and the Windows form to show back. Refused in plain words, "Nothing was changed.": text that is not a full
  drive path (a network share, `\\?\`, a dot part, a `..`, a bad character), a slot with nothing shared, a path outside the shared
  folder, and a folder shared for another use.
- `windows_form(container_path, environ)` and `saved_words(...)`: a file in a shared folder is named in Windows form with the user
  name hidden by `platform.host_shown` (the rule every refusal already follows). A path in `/data`, `/clark` or with `..` gets no
  answer, so the caller keeps what it said before.
- Everything is off unless `CLARK_HOST=windows` and the process really is in a container (`platform.container_mode`). On the Mac
  and plain Linux nothing changes.

## Wiring (the next step, after the wording is ruled)

1. Settings (built for the pasted client folder only): the backup copy folder (`settings.set_backup_copy_folder`), the client folder (`projects.publish_client`) and the local
   folder take the typed path through `to_container` and save the container path; the box shows the Windows form back. The existing
   checks (not the data folder, writable, make a missing last folder) run on the container path unchanged.
2. After Publish, After Excel export and After Word export: the page uses `saved_words` where it now names the file only.
3. To client: `to_client.RealFs` is the only writer and already writes to the saved client folder; the saved value is a path under
   `/shares/client`, so it cannot be a data folder. OneDrive is allowed here (outputs), never for the data folder (#427's check
   stays).
4. item 629 adds the one reader of `CLARK_HOST` in `platform.py`; this module then calls that instead of reading the setting itself.

## Answer to item 623 done-when 3 (how a file reaches the Windows side)

Recorded as the design choice, not yet confirmed on a Windows laptop (item 623 is still open): a shared writable folder, `/shares/files`,
which Docker Desktop shows as a normal Windows folder, so a published file, an Excel export and a Word export are ordinary files the
person opens in Explorer. A browser download is the fallback for a person who shares no folder. To confirm on the laptop: that a
file written in the container appears at the typed path, and that a OneDrive-synced folder shared in accepts writes.

## Not built, and why

- Wiring step 1 is built for the client folder only, and only for a pasted path (`publish_flow.client_folder`, action paste). Not
  built: the backup copy folder (`settings.set_backup_copy_folder`, called from `safety.py`), the local folder (its route chooses a
  folder with the system dialog, which a container cannot show), and the Choose folder button on Windows.
- Done-when 2 (the saved-file wording after Publish, Excel export and Word export) is not built: `saved_words` is ready and tested,
  but no route calls it. The sentences shown after those actions are made in `publish_flow.py`, `word_route.py` and the page, none of
  which is on the CODEOWNERS list. `platform.py` is not on it either; item 629 owns the one reader of `CLARK_HOST`.
- Done-when 3 (To client copying into the shared client folder) is not confirmed: the saved path now can be under `/shares/client`,
  but the copy itself was not run against a shared folder.
- Not checked: that the Settings page lets a typed `C:\` path through to the paste request.
- The compose file itself (a Windows variant, a start command): it belongs to item 623/#427 and the file lists the package-layout tests check.
- Spelling a shared folder into the compose file for the person: they type the path once in the start command.
- Ask clark source folders: off on Windows (owner's decision, 05-11-2026), so no slot.
