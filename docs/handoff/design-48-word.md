## 0. What exists today
- **No Word template is in this repo.** The demo brand is `src/clark/brand/tokens.css`. creaite has `weekly-report-template.docx` and `client-report-template.docx` (21 parts each, one logo picture in `word/media`). They are not copied: a picture in them may be a real brand (RULES: a real client brand stays in `system/branding/`, never committed). The v0.3 default is therefore drawn by code, with the demo tokens.
- **creaite's `docx_tools.py`** (937 lines, not guarded) fills `{{NAME}}` placeholders by regular expression over the XML text, repeats a paragraph or a table row once per list entry, refuses to write if a placeholder is left unfilled ("Not filled: X. Nothing was written."), and reads text by the same regular expressions, one line per paragraph, table cells joined by " | ". It is built for the user's own templates. It is **not safe for a file from outside**: no size or entry limits, no path checks, and it matches a placeholder only when Word kept it in one text run, which Word often does not.
- **The published rows** are what `publish.select()` returns: `{"data", "sections", "tabs", "as_at"}`. It already applies the allow-lists, `client_visible`, `report_hidden`, labels set to exclude, hidden sections, and `PUBLISH_FIELDS` (so `internal_note`, `movement`, `source`, `reasoning`, `options` and `response_action` are not in it). There is one report (FR-82), so there is **no separate team Word file**: Word carries what the HTML carries.
- **Two cleaners exist.** `publish.py` still uses its own `clean_html` (it keeps `img` with `data:`, `h4`, `u`, tables). `sanitise.clean_html` is the authoritative allow-list (#66a) and has no `img`. `publish.py` does not call it yet. Word uses `sanitise`.
- `publications.word` (0 or 1) is in the schema; `Store.log_publication` writes 0 and has no argument for it.
- Excel import (`excel_import.py`) already has `ImportPlan`, `StagedChange`, `Problem`, the writer call `_try` (one step, all or nothing, Undo) and the fingerprint rule that stops new rows being made twice. Its reader is tied to openpyxl sheets.

## 1. What goes into the Word report
One file, built from `select()`'s output and nothing else. The build reads only named fields of it, so an extra key in a row is never written.
1. **Title block:** the project name as the title; "Week ending DD-MM-YYYY" (or "As at DD-MM-YYYY" with none); a small table of code, client, sponsor and phase, only the ones that have a value.
2. **The sections, in the published order** (`sections`, already sorted, hidden ones already gone), each a Heading 1 with the section's own title:
   - **Current state:** the project's `current_state`, rich text. Left out when empty (as FR-14c leaves an empty template out of View, the page and the Word file).
   - **At a glance:** the health in words ("Project health: At risk") with its colour as a fill, the health reason under it, then the tiles from `glance.tiles(..., for_client=True, kept=...)` in a one-row table (title, value, detail). Only tiles whose section is published.
   - **Use cases:** a table of reference, use case, status, headline and the "n open, n overdue" words from `glance.use_case_strip(for_client=True)`; then, for each use case with a "Where it stands" text, a Heading 3 and that rich text, and the ids of its linked published work items.
   - **Milestones:** a table of ID, milestone, owner, agreed date, forecast (or "Achieved DD-MM-YYYY"), the state as the client's word (`state_word`: "Expected later", "Late"), the slip in days and the percentage. The client wording and the state reason sit under the name. A Cancelled milestone is left out, as the page's own client list leaves it out (`milestone_rows.for_client`).
   - **A text section:** its title and its rich text body. Left out when empty.
   - **Risks and issues, Actions, Decisions:** one table each. The text shown is the row's `client_message` when it has one, else the row's own words (data-model.md: "when it is empty, the published page shows the item's own text"). Actions add the latest update under the text. Status, priority, impact and likelihood are words first and a static colour second (never colour alone). An open row past its date says "overdue" in words as well as red. A decision shows the date made, or "Needed by", and what it replaces.
   - A shown section with no published rows says "None recorded." (creaite's own words), so a quiet Risks table is not mistaken for a missing one.
3. **Not carried:** links between items, labels, workstream names as headings, pictures (see Q5), comments, and the editor's tile order and outline colours (`glance_tiles` is not in the published rows, so the page shows the defaults too).
4. **Rich text** (`current_state`, `standing`, a text section's body) goes through `sanitise.clean_html` again, then is mapped paragraph by paragraph: `p`, `h1` to `h3` (Heading 1 to 3 shifted down one, so the section title stays the top level), `strong`, `em`, `s`, `ul` and `ol` (up to three levels), `blockquote`, `hr`, `br`, a checklist box as the characters for a ticked or empty box, and `a` as a Word hyperlink only for `https:` and `mailto:` (an `http:` or `#fragment` link is kept as plain text). Nothing else can be written, because the mapping reads only that tag list.
5. **Dates** are DD-MM-YYYY, words are British English and plain (NFR-3), "clark" is never the start of a line. The file's author and "last saved by" are the fixed word `clark`, never a person; its dates are the report's as-at date, so the bytes are the same for the same rows.

## 2. Where templates come from, and how a template marks its fields
- **v0.3 default: a built-in layout** the code writes (no binary in git, no brand). Colours come from one small table of the demo tokens (`excel_colours.TOKENS`), and a user's own `tokens.css` can pass its values in (six hex digits each, checked, so a brand can never put markup into the file). Font: Arial.
- **A user's own template (the owner's real client templates):** a `.docx` in `system/branding/word/` (git ignores it; found through `platform`), filled by the same blocks. **Markers: `{{NAME}}` placeholders**, not content controls and not bookmarks.
  - *Why:* creaite does it (`docx_tools.py`, since BL-229, with tests), so the owner's existing templates already use it; a person can see and type a placeholder in Word with no Developer tab; and it needs no new skill. *Weakness and fix:* creaite matches only inside one text run, and Word splits runs on a spell-check, an edit or a font change. The fill first joins the runs of a paragraph that holds `{{` (keeping the first run's formatting), then matches. *Why not content controls:* sturdier, but each template would have to be re-made in Word with tags, and the plain text cannot be seen on the page. *Bookmarks:* invisible to the person, and a range does not say what fills it.
  - *Vocabulary (clark's own, not creaite's weekly names):* scalars `PROJECT_NAME`, `PROJECT_CODE`, `CLIENT_NAME`, `SPONSOR`, `PHASE`, `WEEK_ENDING`, `AS_AT`, `HEALTH`, `HEALTH_REASON`; blocks, each alone in its paragraph, `CURRENT_STATE`, `GLANCE`, `USE_CASES`, `MILESTONES`, `RISKS`, `ACTIONS`, `DECISIONS`, and `SECTIONS` (the whole body in published order: the one a simple template needs). A block with nothing to show is removed with its paragraph. An unknown name, or one left over, stops the fill: "The template has a place for X that clark doesn't know" and nothing is written (creaite's rule).
  - *What a fill must preserve:* every part of the template untouched except `word/document.xml` (and the header and footer parts, scalars only): styles, numbering, theme, section properties (page size, margins, headers and footers), the logo, fonts, settings. It adds no part and no relationship except a hyperlink (an external relationship, `https:` or `mailto:` only). Block output uses the template's own style ids (Heading1, Heading2, Heading3, Normal, ListParagraph and its table style) when `styles.xml` has them, and plain formatting when it does not. A template with macros, embedded objects or an outside link is refused by the same checks as an import (section 5).
- **Brand rule:** a real client's template or logo is never committed; the repo's tests build a tiny fictional template in the test itself.

## 3. The build (standard library only)
A `.docx` is a zip of XML parts. `src/clark/docx_build.py`, pure (rows in, bytes out):
- `build(published, colours=None) -> bytes`; `file_name(code, week_ending, as_at, folder=None)` gives `{CODE}-report-{date}.docx` through `platform.safe_name`.
- **Parts:** `[Content_Types].xml`, `_rels/.rels`, `docProps/core.xml` and `app.xml`, `word/document.xml`, `styles.xml`, `numbering.xml`, `settings.xml`, `footer1.xml` (the code, the as-at date and "Page n of N" as fields), and `word/_rels/document.xml.rels` (styles, numbering, settings, footer, one external relationship per hyperlink).
- **Strings:** the XML is written as strings, and **every value goes through one `esc()`** (`& < > "`, and characters XML 1.0 cannot hold are removed first, as `excel_import.NOT_XML` does), so a value such as `</w:t>` is only text. Attribute values (colours, widths, relationship ids, link addresses) are built by the module from checked values, never from row text.
- **Same bytes for the same rows:** members in a fixed order, a fixed time (1980-01-01), a fixed `create_system` and permission bits, relationship ids numbered in order of use, no clock and no random value. (The compressed bytes also depend on the zlib in use; a test compares two builds on one machine.)
- **Size:** a report over the 5 MB cap (NFR-8's published-file limit) is refused in words, as `publish` does.
- **Writing the file** (the route, later): `platform.write_file` (a temporary file, replaced, retried while OneDrive or Word holds it), read back and compared, the name reserved without overwriting unless asked.

## 4. The import: reading Word text into staged items
Reading is **text only** (BRD): never styling, never pictures, never comments, never the address of a link.
1. **The reader** (`src/clark/docx_read.py`, pure): `.docx` bytes in, a list of blocks out: `heading` (level 1 to 9), `paragraph`, `list_item` (level, ordered or bullet) and `table` (rows of cell text), in document order, plus plain-words notes ("2 pictures, drawings or text boxes were not read"). Tracked changes are read as accepted (deleted text is ignored, inserted text kept). Text marked hidden in Word is ignored and counted in a note.
2. **Staging** (later, `word_import.py`): the blocks are mapped by plain code, with no model call, to **new work items only**: a list item or paragraph under a heading that reads Actions, Next steps or Next week becomes a new action; under Risks or Issues a new RAID item (Risk or Issue by the heading); under Decisions a new decision; a table whose header cells match the Excel export's labels (`excel.COLUMN_OF`) becomes rows through the same `from_cell` rules, with ID, Owner, Due, Priority and Status read when present. Anything under another heading is listed in the plan's notes, not staged.
3. **Nothing changes or closes an existing item.** There is no "changed" and no "removed" row: a Word file does not carry ids reliably, and a missing paragraph is not a decision. (Excel stays the round-trip format.) Every staged row is `kind="new"` in the same `ImportPlan` and `StagedChange`, with `before` empty, so the same accept, reject, "accept all" and report code apply.
4. **The user decides:** each row is accepted or rejected by number, as in Excel; nothing is written until then; the accepted rows go in one step through the one writer (`Store.step`, via `excel_import._try`'s pattern), so one Undo reverses the whole import. Each new row's `source` says "Word import, DD-MM-YYYY, file name, under the heading's words" (never published: `source` is in `NEVER_PUBLISH`).
5. **No double import:** the fingerprint rule is reused (SHA-256 over the table and the values read, not the file's bytes), so the same file twice does not make the items twice. This needs the record to live somewhere other than `excel-export-state.json`: the Excel record is keyed by workbook hash and tied to the export; for Word a small `word-import-state.json` beside `clark.db` holds only `{"created": [fingerprint, ...]}`.
6. **Text from a file is not an instruction.** It is plain strings written into plain fields. It goes through the same value checks as any typed text, and a rich field (none is seeded in v0.3) would go through `sanitise.clean_html`.
7. **Client-safety:** a seeded item is created with `client_visible` **off** (Q3), and the plan says so ("Not shown to the client until you turn it on"), so text from an outside file never reaches a published file because of an Accept alone.

## 5. What the reader refuses
The reader is given bytes, never a path, and opens nothing else. It never starts Word, a macro, a link or a network call. Every refusal is one `WordRefused` with a plain message (section 6) and nothing is staged.

| Hostile input | Rule | Limit |
|---|---|---|
| Too big as saved | refuse before opening | 25 MB (as `excel.MAX_FILE_BYTES`) |
| Zip bomb: one part, or all, unpack too big; a very high ratio | the central directory's declared sizes are added up first, and each part is read through a limit, so a size the directory understates is stopped by the limited read (there is no separate overlap check: overlapping parts cannot unpack to more than their declared sizes in total) | 20 MB a part, 50 MB in all, ratio over 200 on a part over 1 MB |
| Too many parts | refuse | 200 (as `excel.MAX_MEMBERS`) |
| Unsafe names: `..`, a leading `/` or `\`, a drive letter, a backslash, a NUL, a repeated name (case ignored) | refuse | none allowed |
| Damaged, cut short, not a zip, empty, a size in the directory that lies | refuse (`BadZipFile` and CRC errors become words) | none |
| Password protected (the zip flag, or an Office encrypted file) | refuse | none |
| Not a Word file: no `[Content_Types].xml` or no `word/document.xml` | refuse | none |
| **Macros:** `vbaProject.bin`, `vbaData.xml`, `vbaProjectSignature.bin`, a `macroEnabled` content type | refuse the whole file | none |
| **Embedded objects:** anything under `word/embeddings/` or `word/activeX/`, an `oleObject` or `package` relationship | refuse the whole file | none |
| **Outside links:** a relationship with `TargetMode="External"` that is anything but a hyperlink (attached template, linked picture or object, frame, sub-document, external data) | refuse the whole file | none. A hyperlink (its relationship type compared whole, in either Word spelling, never by its ending) is allowed and **not read**: its text stays, its address is dropped |
| XML with a definition: any `<!DOCTYPE` or `<!ENTITY` (billion laughs, external entities, parameter entities) | refuse before parsing; Word never writes one | none |
| Not UTF-8, or a declared encoding other than UTF-8; text Python cannot decode | refuse | none |
| Deep or huge XML | parsed as a stream (expat's own start, end and text handlers) that clears what it has used; stops the moment a limit is crossed | depth 64, 2,000,000 elements |
| A giant paragraph, or a flood of blocks | refuse | 200,000 characters a paragraph (`sanitise.MAX_CHARS`), 50,000 blocks, 5,000,000 characters in all |
| Text a person could not see (hidden runs, deleted text, text in pictures and text boxes) | not read; the first is noted | n/a |

No part of the standard library's parser fetches anything: with no DOCTYPE allowed there is no external entity to fetch, and a test makes any socket call fail. The same checks run before a template is filled (section 2), because a template is also a file from outside until the user has chosen it.

## 6. Plain-words errors
No "zip", "XML", "entity", "relationship", "traceback", "DTD" or part names in anything a person reads (a test pins this, as `test_every_message_is_plain` does for To client). The messages, each naming the file:
- "{name} can't be opened as a Word document. It may be damaged or cut short. Open it in Word, save it again as a .docx and try again."
- "{name} is {n} MB, more than the {m} MB clark will open. Save a smaller copy and try again."
- "{name} would open to about {n} MB, more than the {m} MB clark will open, so it was not read. Remove large pictures or split it, then try again."
- "{name} looks packed in an unusual way, so it was not read. Open it in Word, save a copy and try again." (the squeeze-ratio rule)
- "{name} is too complex for clark to read, so it was not read. Save a simpler copy and try again." (too many parts; the word "parts" is never shown)
- "{name} has something inside it clark can't open safely, so it was not read. Open it in Word, save a copy and try again." (an unsafe or repeated name)
- "{name} is not a Word document: it has no main text."
- "{name} has macros in it. clark never opens macros. Save a copy as a plain .docx (not .docm) and try again."
- "{name} has a file or object inside it (such as a spreadsheet). clark won't open it. Remove it in Word and save a copy."
- "{name} is linked to something outside the file (a template or a picture at an address). clark won't open it. Break the link in Word and save a copy."
- "{name} is password protected, or is an older kind of Word file. Open it in Word, remove the password, save a copy as a .docx and try again."
- "{name} has text clark can't read safely. Open it in Word, save a copy and try again."
- "A paragraph in {name} is longer than {n} characters, so it was not read. Split it into smaller documents and try again." (the same next step ends "holds more text than clark will read" and "holds more than {n} paragraphs and rows")
- The notes: "The web address of 1 link was not read; the words stay." and "The web addresses of {n} links were not read; the words stay."
- The import plan says "waiting", then "accepted" or "rejected" (never the internal state), uses proper plurals ("1 action", "2 risks or issues"), says "There is no item {n} in this list.", and ends a risk-or-issue refusal with what to do ("Add a Type column or start the line with Risk or Issue.").
- The Word report: "The report could not be made: ... Restart clark and try again.", "The report is {n} MB, which is over the {m} MB limit. Leave out some sections or pictures and try again.", and the label "Latest update:".
- Export: "{file} could not be saved ({reason}). If it is open in Word, close it and try again. Nothing was written." and the report-too-big message.

## 7. Proposed Done-when (for the Head's readiness check)
1. **Build is pure and repeatable.** The same published rows give the same bytes twice; the result is a zip whose every part parses, whose content-types list covers every part, and whose relationships all point at a part or an `https:` or `mailto:` address.
2. **Only the published rows.** From the #39 plant (`publish-plant.json`), every kept marker is in the file and every dropped marker, in four spellings (`spellings()`), is in no part; a field outside `PUBLISH_FIELDS` planted in a row is never written; a hidden section, a flag-off row, a Sensitive row and an archived row are absent.
3. **Content.** Sections are in the published order; the client's words are used for milestones; `client_message` replaces a row's own text when present; dates read DD-MM-YYYY; health, status and priority are words; a quiet table says "None recorded."; an empty current state or text section is left out; one test for each.
4. **Rich text** goes through `sanitise.clean_html`: script, style, event attributes and `javascript:` links never reach the file; bold, italic, strike, headings, lists to three levels, quotes and an `https:` link map as written; a text of 200,000 characters builds.
5. **Template fill** (if Q1 is answered as recommended): a fictional template made in the test is filled; every untouched part is byte for byte the template's; a placeholder split across runs is found; an unknown or unfilled name stops the fill and writes nothing; a macro, embedded or linked template is refused.
6. **Word export file** (waits for #65 and #77): `{CODE}-report-{date}.docx` is written with `platform.write_file`, read back and compared; a name already taken asks (design-43's choices); `publications` gets one row with `word` 1 and the file's SHA-256; it is never written into a client folder except with To client ticked.
7. **The reader refuses every row of section 5**, one test each, each with its plain message and no staging; it never opens a file, a socket or a process.
8. **The reader reads a good file:** a file built by `docx_build` reads back to the headings, paragraphs, list items and table rows of the report; a Word-made fixture with tracked changes, hidden text, nested lists, a merged cell and a text box reads as section 4.1 says.
9. **Import staging** (waits for the store step and the route): only new items are staged; nothing is written until accepted; "accept all" and by-number work; the step is one Undo; `source` is set; the same file twice makes the items once; `client_visible` is off (or as Q3 is answered); a bad row names itself in words and the whole step rolls back.
10. **Windows readiness:** every `open()` names UTF-8, no system command outside `platform`, file names pass `platform.safe_name`, and the zip's member names use `/`.

## 8. Windows
Nothing here calls a system command. The reader takes bytes and the build gives bytes, so only the route touches a path: `platform.safe_name` and `platform.write_file` (Word and OneDrive hold open files, and `os.replace` fails then; the existing retry and the plain "close it in Word" message cover it). A Word lock file `~$name.docx` is not a zip and is refused as damaged. Zip member names are always `/` and ASCII, `create_system` is fixed (so a Windows build writes the same bytes), and the state file is written with `platform.write_file`. Opening the result afterwards is `platform.open_file` or `reveal_file`.

## 9. What is built now, and what waits
- **Built (step 2, pure, no route, no store, no page):** `src/clark/docx_build.py` (the built-in layout from published rows to bytes; `sections()` makes the body block by block so the template fill can reuse them) and `src/clark/docx_read.py` (bytes to blocks and the refusals), with `tests/test_docx_build.py` and `tests/test_docx_read.py`, and a row in the reuse record. Done-when lines 1 to 4, 7 and 8 (the round trip) and the Windows source check of line 10 are covered by them; 5, 6 and 9 wait.
- **Built since (pure staging):** `src/clark/word_import.py` (`stage(read, file_name, imported_on, seen)` gives a `WordPlan` of new actions, risks and issues, and decisions, each `client_visible` 0, with accept, reject and a plain report) and `tests/test_word_import.py`. It imports no store; the guarded step that writes `WordPlan.accepted()` is a separate PR.
- **After review:** a heading longer than `MAX_HEADING` (80) characters is not one of the names, so it is never scanned (the trailing-punctuation strip is `rstrip`, not a regex) and never copied into a row's `source` or `where`; a block's `level` that is not a whole number counts as 1. Two identical lines in one file are staged once and counted in the report as "left out because they were added before or repeat another line". **For the store step:** a table line may stage a decision as Made (with a date); Made decisions created by an import must be in the shared `UNDOABLE` table when the writer lands, so one Undo reverses them.
- **Waits:** the template fill (Q1); the staging and `word_import.py` (Q3 to Q5 and a store route, Q4); `/api/export-word` and the Publish dialog's Word tick (#65, #77, the owner); the `publications.word` write (a guarded `store.py` change, Q2); the profile-menu entry.

## 10. Open questions
1. **The owner: how does a template mark its fields?** *Recommend* `{{NAME}}` placeholders (section 2), with the user's templates in `system/branding/word/` and the built-in layout as the default. The other choice is content controls, which means re-making each template in Word. Default: placeholders.
2. **Head (guarded `store.py`): `publications.word`.** *Recommend* a `word` argument on `Store.log_publication` (0 or 1), one row for the Word file beside the HTML's, the same SHA-256 rule; the Publish dialog gets a "Word too" tick and the profile menu an "Export to Word" entry (#77), both on one code path. Needs your ruling on the guarded edit. Default: that.
3. **The owner: are items seeded from Word shown to the client?** *Recommend* off: the schema default is on (#24), so an Excel-imported or typed row is published, but text from a file nobody has read closely should not reach the client because someone pressed Accept. The plan says so and the user turns each one on. Default: off.
4. **Head: the import's route.** `change_log.route` allows `dashboard`, `assistant`, `excel`, `undo`, `client`, `team`, `migrate`. *Recommend* adding `word` to the schema's CHECK and to `store.ROUTES` (a small guarded edit, Full review); the other choice is to record a Word import as `excel`, which would make Activity say "Excel" for a Word file. Default: add `word`.
5. **The owner: what may an import seed?** *Recommend* new actions, RAID items and decisions only (section 4); Current state, text sections, milestones and use cases are not seeded in v0.3, because each would replace or need dates and agreement. Also: pictures. `sanitise` allows none, so Word carries none, while `publish.py`'s older cleaner lets an embedded picture into the HTML. *Recommend* no pictures in Word in v0.3. Default: that.
6. **Head: reuse of the Excel import.** `ImportPlan`, `StagedChange`, `Problem` and `_try` can be used as they are; `apply_import` and its state file are Excel's. *Recommend* `word_import.py` has its own small apply and state file and calls `_try` (with the route as an argument: a one-line change to `excel_import.py`, owned by #38). Default: that.
7. **For the Head, not a question:** `publish.py` still uses its own `clean_html`, not `sanitise.clean_html`, so the page and Word can differ on `u`, `h4`, tables and pictures until #66a is wired in. Word runs the sanitiser itself and so is the stricter of the two.
