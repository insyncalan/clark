## What is true today
- Nothing of the five kinds (projects, work items, milestones, use cases, documents) is hard-deleted by any route. A cancelled action or RAID item is a status; a project "cancel" sets `active = 0`.
- No archive code exists. The `archived` column exists on `projects`, `milestones`, `workstreams`, `actions`, `raid`, `decisions` and `use_cases`; `projects` has `CHECK (archived = 0 OR active = 0)`. `documents` has no `archived` column and is not in `TABLES`, `KEYS` or `REQUIRED_NEW`.
- `refuse_archived_field` (`store.py:696`) refuses `archived` in every new row and update. Nothing sets it. Reads already leave archived rows out of the page's data (`data_for`), the export, the glance counts, the milestone rows and `publish.select`.
- `_project_exists` (`store.py:395`) already refuses a new or changed row in an archived project: "restore it first".
- The only `DELETE FROM` statements in `src/` are `delete_row` (`store.py:877`: links, item labels, labels, report sections, glance tiles, hidden flags) and the undo of a creation in `revert_group` (`store.py:1130`).
- `/api/change` admits one kind, `report_sections` (`changes.py` `CHANGE_KINDS`). `/api/undo` only undoes a step made of report sections (`_eligible`).

## The rule, in plain words
Archive hides a record. It deletes nothing and changes no status. An archived record leaves the default views, the counts and the published page; "Show archived" finds it; it opens read-only with Restore; its history stays; Restore brings it back; each archive or restore is one step with one Undo. Cancelled stays a status, separate from Archive (a Cancel menu item stays; Archive is another action).

## The two operations
`Step.archive(kind, ref)` and `Step.restore(kind, ref)`, beside `Step.cancel`. They are the **only** setters of `archived`.

Kinds: `projects`, `milestones`, `actions`, `raid`, `decisions`, `use_cases`, `documents`. Workstreams (which have the column) are archived only with their project; they get no single-row archive in v0.2 (question 9).

`write_item` gains `op: archive` and `op: restore`. Each builds its own change (`{"archived": 1}` or `{"archived": 0}`, and for a project the `active` change below) and goes through the existing `_update_row`, so the checks, the `updated_at` stamp and the `change_log` rows are the ordinary ones. Rules:
1. `archived` stays on the "never in a new row or an ordinary update" list. `refuse_archived_field` is kept for `new`, `update` and `cancel`, reworded ("archived is set only by archive or restore"). It is not removed: it is what keeps `Step.update` from writing the flag.
2. An archived row refuses every update, cancel and label change except `restore`: "X is archived: restore it first". This is the read-only behaviour, enforced in the writer, not the page. A new link to or from an archived item is refused the same way (question 6).
3. Archive of an archived row, and restore of a live one, are refused in plain words (not silently ignored), so a double click makes no second step.
3a. **Revised (name clashes, a teammate MEDIUM 4).** Restore re-runs the full row rules on the restored row, so any clash, now or added later, is a plain refusal that names the thing and the way out. Archive validates only the change it makes (`archived`, and `active` for a project), as the Undo path does with `revert`; it does not re-run the other row rules on the merged row, so a legacy row that breaks a later rule (an old milestone or decision) cannot make "archive this project" fail on that child. Today a restore cannot clash: `workstreams` has `UNIQUE (project, name COLLATE NOCASE)` over all rows including archived ones and `_workstream_unique` ignores `archived`, so an archived workstream keeps its name reserved; item IDs are never reused and project codes are primary keys. But that reservation hides a trap: a new workstream with an archived one's name is refused with "already has a workstream called X (ABC-W-002)" and does not say it is archived. The message gains "(archived)" when the holder is archived. A test plants a clash (a row that would break a rule on restore) and restores it: refused in plain words, nothing changed.
4. The flag is validated as 0 or 1 like the other flags (`archived` moves from `FLAGS_ELSEWHERE` into `FLAG_COLUMNS`; `test_store_flags` keeps passing).
5. Restoring a child of an archived project is refused by `_project_exists`: restore the project first.
6. Restoring does not change status. An action archived while Open comes back Open.
7. Item IDs are never reused: `next_id` already counts every ID in `change_log` as well as the table.

## Undo
Undo is `Store.undo(step_id)` unchanged: a new step whose rows put each old value back. Two small changes make it work for archive:
- `revert_group` writes through `write_item(..., revert=True)`. Today that path would be refused for `archived`. With `revert=True`, and only then, `archived` is permitted and the "archived row is read-only" rule is skipped. `revert` is set only inside `revert_group`; `Step.update`, `Step.archive` and the routes cannot pass it. A test pins this: no other code sets `revert`, and `Step.update` with `archived` still raises.
- Order falls out right. `revert_plan` reverses groups newest-first. A project archive writes children first and the project last, so its Undo restores the project first and the children after, which is what `_project_exists` needs. The Undo of a project restore (project first, children last) re-archives the children first and the project last. Neither needs special code; a test pins each.

One archive or restore = one `applies` row = one Undo. An Undo of an Undo works as for any step. A row changed since is skipped and named, as today (for an archive, "changed since" means a later step restored or edited it).

## Project archive: the step order
All inside one `Store.step` (one `BEGIN IMMEDIATE`, so a failure leaves nothing half done):
1. Refuse if the project is missing or already archived.
2. Archive the **children first**, each with `archived = 1`, in a fixed order: workstreams, milestones, use cases, actions, RAID items, decisions, documents. A child already archived is skipped and not logged.
3. Archive the **project last**: `archived = 1` and `active = 0` (the CHECK needs both, in the same `UPDATE`).
4. Left alone: links, labels and item labels, updates (weekly), report sections, tiles, hidden flags, publications. They are annotations and layout; they stay readable and the page shows them.

**Restore**, in one step, in the reverse order:
1. Refuse if the project is not archived.
2. Restore the **project first**: `archived = 0`, and `active` put back to what it was before the archive (below).
3. Restore the children **that the project's last archive step archived**, found from `change_log` (the newest `projects` row with `field = 'archived'`, `new_value = '1'`, then its `apply_id`). A child that was archived on its own before the project was archived stays archived. If that step cannot be found (a database brought in from elsewhere), only the project is restored and the reply says so.

`active` on restore (decide and tell, reversible): restore sets `active` back to the `old_value` of the `active` row in the archive step. If the project was already inactive when archived, no `active` row was logged, it stays 0 and the project comes back closed, as it was. Restore never invents a reopening. (The other choice, always `active = 1`, would reopen a project the user had closed; question 4.)

Cost: one `change_log` row per archived record and field. A large project writes some thousands of rows in one transaction; that is fine for SQLite and is the price of one-step Undo.

## The `schema_version` 2 migration (documents)
- `schema.sql`: `documents` gains `archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1))`. A new database is made at version 2 directly (`SCHEMA_VERSION = 2`).
- `TABLES`, `KEYS` (`("project", "id")`, key string `ABC|<id>`, as `item_labels` does) and `REQUIRED_NEW` (the table's NOT NULL columns: `project`, `title`, `url`) register `documents`. This only makes the table archivable. How a document is created, its ID and its screens belong to its own item (question 8).
- **Revised (a teammate MEDIUM 2).** `documents` has no `updated_at`, no ID scheme and no rule for `url` (`doclinks`, #74, allows only http, https and mailto). Once registered in `TABLES`, `Step.create("documents")` and `Step.update("documents", ...)` would be reachable from any store caller with none of those checks. So the writer refuses, for `documents`, `new` and every `update` except archive and restore ("documents are added in their own item"), until the documents item brings its rules, `url` through `doclinks` included. This is enforced in the writer, with a test for each refused op. Every reader of documents (`data_for`, `publish_inputs`/`select`, the export, Word, and any the build or #74 adds) must filter `archived = 0`; `store.py` reads documents nowhere today, so the rule belongs in each reader's own test.
- `open_store`: after the existing checks, `if version < 2: migrate_to_2(con)`, inside one `BEGIN IMMEDIATE`: if `archived` is not already a column of `documents`, `ALTER TABLE documents ADD COLUMN archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1))`; then `UPDATE meta SET v = '2' WHERE k = 'schema_version'`; `COMMIT`, or `ROLLBACK` on any error. It is idempotent, and the column check makes a half-applied copy safe.
- A database already at a **higher** version is still refused. A version-1 clark opening a version-2 file says "made by a newer clark" (existing text).
- Other tables need no migration: the column is already there. A migration is not a step: it writes no `applies` row and has no Undo.
- **Revised (a teammate MEDIUM 1; question 5 decided YES by the Head).** Two things, both needed:
  1. **Copy first.** Before `migrate_to_2` begins, `open_store` takes a safety copy through #86's own `backup.make` (tag and family `migrate`, below), and **refuses the migration, in plain words, if the copy cannot be made** (as an import is refused). The transaction alone is not the safety net: it does not cover a bug in the migration that commits. A test forces the copy to fail and checks the version-1 file is untouched and still version 1.
  2. **`check_copy` accepts older copies.** #86's `check_copy` refuses a copy whose `schema_version` is below `SCHEMA_VERSION` ("made by an older clark (version 1)... can't be put back"), and `restore` goes through it. The day `SCHEMA_VERSION` becomes 2, every existing backup is a version-1 file and restore would refuse all of them. `check_copy` therefore accepts any version from 1 up to the current one (a restored older file is migrated by `open_store` on the next start, by the same code as a live file); a newer one is still refused. A test restores a version-1 copy and opens it. `check_copy` is in #86's file, so the change is named in commit 1 (or in #86 if it lands first).
- **Revision 2: the copy's tag.** One choice: its own `migrate` family, not `restore`. In the `restore` family a run of restores could evict the one copy made before the migration. `backup.py` fixes the tags, the families and the file-name pattern (`TAGS`, `FAMILY`, `NAME`), so this is a change to #86's guarded file: `migrate` is added to all three, with its own test that retention keeps the newest `migrate` copy whatever the other families do, that the restore list shows it, and that `check_copy` accepts it. It is its own small commit (commit 0 below), made **after PR #56 (#86) merges**, rebased on it.
- **Revision 2: when no copy is taken.** A database being created new (no file yet) takes no copy: there is nothing to lose. A copy is taken only when an existing file is at version 1. If two windows both find a version-1 file, each may take a copy; that is harmless.
- **Revision 2: what the person reads when the copy fails.** "clark could not make a safety copy of your data before updating it, so it has changed nothing. Your data is exactly as it was. Please check that there is room on the disk and that the folder [folder name] can be written to, then open clark again." The folder named is the backup folder; the message says nothing was changed, and a test checks both.
- **Revision 2: two windows, one version-1 file.** `migrate_to_2` re-reads `schema_version` after `BEGIN IMMEDIATE` and does nothing (commits an empty transaction) if it is already 2, so the second window does not migrate twice. A test opens one version-1 file from two connections in turn and checks one migration, version 2, and the rows unchanged.
- **Revision 2: what version 1 means.** `open_store` applies `schema.sql` only when it creates a database, and `report_sections`, `glance_tiles` and `report_hidden` were added to `schema.sql` with no version bump. So `migrate_to_2` first runs the idempotent `CREATE TABLE IF NOT EXISTS` statements from `schema.sql` (tables only, in the same transaction, before the `documents` column), and any older working file migrates correctly; nobody needs to be asked whether a file predates #65. A test uses a version-1 file that lacks those three tables: it opens, gains them and the column, and is version 2.
- `data-model.md` and its `documents` DDL are updated in the docs commit.

## Routes (`changes.py`, `server.py`)
- `CHANGE_KINDS` gains the seven kinds, each with `{ARCHIVE: (), RESTORE: ()}` (no fields: an archive takes no values). Ops are built from one string like the others, so the writer test's SQL scan is not fooled; the request names no table, column or SQL. `OP_KEYS` for both is `("id",)`. For `projects` the `id` must equal the request's `project` code (anything else is refused with the same words as another project's row).
- `_do_change` is split by kind: the section code stays as it is; archive and restore call `Step.archive` / `Step.restore` under the same lock and the same `BEGIN IMMEDIATE`. The reply carries `apply_id`, the `ref`, `archived` (0 or 1) and, for a project, counts by kind. Never a body.
- `_eligible` (the Undo check) is widened. **Revised (a teammate MEDIUM 3):** it checks the field, not just the table. Once `actions`, `raid`, `decisions`, `milestones`, `use_cases`, `projects` and `documents` are in `CHANGE_KINDS`, a table-only test would let `/api/undo` undo any dashboard step that touched them (a future peek edit, a title change), although `/api/change` offers only archive and restore. So: a step is the dashboard's to undo when every row was written via the dashboard, is not an undo, and either is a `report_sections` row as now, or is in one of those tables with field `archived` (or, in a project's archive or restore step, `active` on the project's own row), and the key belongs to this project. Key test: the prefix test keeps the dash or bar (`ABC-` for items, `ABC|` for documents), so project `ABC` never matches `ABCD-...`; a project's own row has the bare code as its key, so it matches when the key **equals** the code. A project archive step has many rows; all must pass. `words()` gains phrases for archive and restore. Tests: a dashboard step that edits a title in these tables is refused by `/api/undo`; `ABC` does not match `ABCD-A-001`; the project's own row (key `ABC`) passes.
- `server.py`: `/api/data` takes `?archived=hide|show|only`, `/api/projects` takes `?archived=1`; both are checked against a fixed list, not passed on. `ROUTE_BODY_LIMITS` is unchanged.
- **ask clark and the AI menu** reach the store only through `Step.archive` / `Step.restore` (or `/api/change`); neither has a delete. Today only `changes.py` and `excel_import.py` open a step (`glance.py` names `Step.update` in a docstring), so there is nothing to rewire yet. A test pins that no module outside `store.py` contains a `DELETE FROM`, and that `delete_row` refuses every table outside the annotation list. **Revision 2:** because report sections are exempt, the scan stays exact: no `DELETE FROM` anywhere in `src/` except `delete_row` (annotations, report sections, tiles, hidden flags) and the undo of a creation in `revert_group`, and the scan names both.

## Questions for the Head/the owner
Each is a place where a choice would loosen a guard or bend the rule. The plan above uses the stated default in every case and assumes nothing more.

1. **Links, labels and item labels.** Are these "records" under the rule? Default: no, they stay hard-deleted annotations (each deletion keeps the row in `change_log`, and Undo restores it). Making them archivable needs columns and a rule that an archived item's links are hidden.
2. **Report section Delete (text sections).** **Closed (Revision 2).** The owner ruled (BRD FR-43c, commit a95e9c5): report sections are exempt. "Delete this section" stays, for text sections only, with an Undo toast. No column on `report_sections`, no second migration step. Records still archive.
3. **Undo of a creation** stays a hard delete (decided on the issue). Should a new document's creation be undoable by deletion too? Default: **no** (documents are not added to `REVERT_CREATED`), the tighter choice.
4. **Restore of a project: `active`.** Default: back to what it was. If a restore should always reopen (`active = 1`), say so; it is a one-line change but reopens a project the user had closed.
5. **Safety copy before the migration.** **Closed: yes (the Head, 28-10-2026), through #86's `backup.make` in its own `migrate` family (Revision 2).** The earlier `clark.db.v1` idea and the "no copy" default are withdrawn.
6. **A new link to or from an archived item.** Default: refused ("restore it first") in `check_link`. That is a new rule in guarded code; the alternative leaves a live item pointing at a hidden one.
7. **Archiving a record that live records still point to** (a milestone or use case with open work items). Default: allowed, no cascade, no warning from the writer; the page should warn. A stricter writer rule (refuse while live items refer to it) is not proposed.
8. **Document creation.** *Revised: `new` and `update` on `documents` are refused in the writer until the documents item (see the migration section).* `documents` has no ID scheme (`next_id` and `ID_PREFIX` do not know it) and no create rules. Registering it in `TABLES` makes `Step.create("documents")` reachable. Default: this issue adds only archive and restore for existing rows. Who owns creation (FR-100), and should `Step.create("documents")` be refused until then?
