# Design note: the restore race that is still in `open_store` (#185 follow-up, "MEDIUM A")

Docs only, 30-10-2026. Nothing is built. Review tier: Full (guarded files); see sections 7 and 8. Revised after the first code reader's read of a2874416. Base: `origin/main` ada9644a (the #185 code is byte-identical to c5282d5 there).

## 1. What is already fixed, and what is not
PR #185 added `backup._UNDER_WAY` (the databases a restore is working on in this process). `restore_path` sets it for its whole run and clears it in `finally`. `finish_restore` raises "A restore is under way. Wait a moment and reload." when the flag is set. That closed the first reported case: a read that arrives after the restore note is written and finds `clark.db` moved aside.

Not closed: **the flag is only looked at after the note exists.** In `finish_restore` the order is: clear old working files; `if not marker.exists(): return`; only then the flag test. The note is written late in `_restore_path` (after the safety copy and the big file copy). Everything before that line, and the gap between a reader's check and its connect, is unguarded.

## 2. The races, each with a sequence
Reader R is any thread that calls `open_store` without the change lock: `GET /api/projects` (`projects_of`) and the Publisher (`publish_flow.store()`). W is the restore.

**R1. A reader passes the check just before the note, then connects after `clark.db` has moved (the reported one).**
1. R: `open_store` -> `finish_restore`: no note, so it returns.
2. W: writes the note, moves `clark.db` aside.
3. R: `connect(path)`. The file is gone, so SQLite makes a new empty `clark.db`, and `PRAGMA journal_mode=WAL` makes a `-wal` and `-shm` beside it.
4. R: sees no tables, so it takes the "new database" branch: `BEGIN IMMEDIATE`, builds the schema, inserts a fresh `db_id`, and returns a Store on an empty database.
5. W: its loop moves `-wal` and `-shm` aside, which are **R's**, into the folder that holds the old `clark.db`. Then it replaces R's empty file with the restored copy.
Results: (a) the old data in `replaced-*` is now paired with a stray WAL that is not its own, so "move clark.db back" (the advice we give) may give an empty or damaged database; (b) R's connection points at a file that no longer has a name, so anything R writes is lost; (c) on Windows an open handle makes the final replace fail (the retry in `platform.py` gives up), and the restore says "Nothing was changed" although the old database is already in `replaced-*`. Nothing is lost outright: the safety copy and the old `clark.db` alone still hold the data.
Why the flag does not help: it is set from the start of `restore_path`, but R never reads it, because there is no note yet at step 1.
The empty file R makes in step 3 is not harmless even if R stops there. The restore code reads "`clark.db` exists" as "the old database was never moved". If the restore then stops before its final replace, the next start tidies up the note and builds a new empty database in R's file, with no pointer to the old data in `replaced-*`. If the final replace fails, the restore says "Nothing was changed" while the old database is already in `replaced-*` and the live file is R's empty one.

**R1b. A reader connects after the move loop and before the final replace.** The loop has moved `clark.db`, `-wal` and `-shm` aside. R connects now, so SQLite makes a new file and WAL beside the name. W's final `replace_file` puts the restored copy next to R's `-wal` and `-shm`, which are not its own. The restored database then reads as **empty** (0 projects where the copy has some) until R's WAL is dealt with, and the next checkpoint would write R's pages into it. The chosen backup is still in `backups/`, so nothing is lost for good, but the restore looks as if it wiped the data. The same fix closes it (section 3).

**R2. A reader during the long part of the restore (before the note).** After the flag is set and before the note is written, `finish_restore` returns at once. If R connects now it succeeds (the file is still there; the "in use" probe only blocks it after the second look). It is harmless to the swap, but R may then hold an open connection across it (R3). Today the person gets data or a 5-second wait, not "wait and reload". This is the same missing check as R1, seen earlier.

**R3. A connection opened before the swap and kept across it.** The "in use" probe refuses a busy file, but an idle connection (no statement running) does not block it. After the swap, that connection still points at the old file, now in `replaced-*`: reads show old data, writes are lost. In today's code the only long-lived one is Publisher's `publish()`: it opens the store, writes the page, and logs the publication row at the end, without the change lock. A restore in the middle would lose that row. This is **not** an `open_store` fault; it needs the restore to wait for (or refuse while) a publish runs.

**R4. First-run creation uses the same door.** `open_store` is also how a new data folder gets its database. Anything that reaches the "no tables" branch while a restore of the same path is running (R1 step 4) makes a database nobody asked for. The creation branch has no guard of its own.

## 3. Smallest fix
1. **`backup.py` `finish_restore` (guarded):** move the flag test above `if not marker.exists(): return` (and above `_clear_marker_parts`). Four lines move; no new line of logic. This alone closes R1 and R2 in practice, because the flag is set before anything is copied or moved, so any reader that checks during the restore is told to wait. `open_store` already calls `finish_restore` first, so it needs no change for this part.
2. **`store.py` `open_store` (guarded), no power to create, plus a second layer.**
   - **No-create open.** When `clark.db` exists at the check, `open_store` opens it with `sqlite3.connect(f"{path.resolve().as_uri()}?mode=rw", uri=True, isolation_level=None)`, the same form `connect(readonly=True)` uses at `store.py:1409`. With `mode=rw` SQLite cannot make the file. Only a path that is missing at the check, with no note and no restore running, goes through the creating `connect` (first run). A reader whose file moves away between its check and its connect gets "unable to open database file"; `open_store` maps that to `Invalid(RESTORE_BUSY)` if `restoring(path)` is true, and otherwise to its existing words. This leaves no stray file, so crash recovery and the stopped-restore messages stay true, and it works on every OS.
   - **Second layer, kept.** A helper in `backup.py`, `restoring(path)` (true when the path is in `_UNDER_WAY`, using the same key as `restore_path`, `os.path.abspath(path)`; `finish_restore` uses it too). One check in `open_store` after `connect` and before the schema is built: if a restore of this path has begun, `con.close()` and raise `Invalid(RESTORE_BUSY)`. It deletes nothing. Every caller of `open_store` now meets `Invalid(RESTORE_BUSY)` for the whole restore, so the build must check that each one (the routes, `changes.py:1064`, the Publisher, `safety.py`, the launcher) turns it into the plain sentence and not a crash.
3. No change to `restore_path`, `safety.py`, `server.py` or `__main__.py`.

Residual, stated plainly: only a path that is missing at the check can reach the creating connect, and the second layer then stops it before any schema or `db_id` is built. A reader that stalls for the whole copy between its check and its connect now finds either the file (opened without the power to create it) or nothing to open (busy). R1 and R1b are closed in full. Across processes, P1 is closed too, on every OS, with no lock (section 5). A shared gate is not needed (Q3).

## 4. Test plan (each test fails on today's code)
All in `tests/test_backup.py`, same technique as the existing `test_111_a_read_during_the_swap...`: patch a step of the restore so `open_store`/`projects()` runs inside it.
- **T1, before the note (R1/R2):** patch `backup.make` (the safety copy; the probe is not held there) to call `open_store` once. Expect `Invalid` with the busy sentence. Today it opens and returns a Store.
- **T2, the empty database (R1):** patch `backup._move_aside` to, after `clark.db` has moved, call `open_store` with `backup.finish_restore` replaced by a no-op for that one call (this stands for "R already passed the check"). Expect the busy sentence, **no** schema in any file R touched, and the restore finishing. Judge `replaced-*` by content, not file names: `replaced-*/clark.db`, opened with whatever sits beside it, gives the old row counts, and its `-wal` is the one that was there before the restore (same size or bytes). The restored `clark.db` gives the restored row counts. Today a new database with a schema and a different `db_id` is made and its WAL ends up in `replaced-*`.
- **T2b, after the move loop (R1b):** patch `platform.replace_file` so a reader that skipped the check runs just before the real replace. Expect busy, no `-wal` or `-shm` beside the restored file, and the restored row count (not 0).
- **T3, creation guard (R4):** put the path in `backup._UNDER_WAY`, replace `finish_restore` by a no-op (so only the second layer can answer), call `open_store` on a path with no file. Expect busy and no file made. This holds because the open has no power to create when the file is missing mid-restore (`mode=rw`), and the second layer answers when the path was missing at the check; a check after a plain `connect` could never pass, since `connect` makes the file first. Today it makes one.
- **T7, a stop after a reader skipped the check:** patch `platform.replace_file` so a reader that skipped the check connects, then stop with an exception that is not an `OSError`. The next `open_store` must finish the restore, or raise `Unfinished`, and must not build an empty database. Today it opens a new empty one and the old data sits in `replaced-*` with no note.
- **T8, a failed final replace after a reader skipped the check:** the same reader, then `replace_file` raises `PlatformError`. Expect the "stopped part-way" sentence and the note kept, not "Nothing was changed". Today the note is removed and the sentence is wrong.
- **T4, the two-thread order (R1 as it really happens):** W and R on threads with `Event` hand-offs (R: run the real check, signal, wait; W: write the note and move `clark.db`, signal; R: connect). Every wait has a 10-second hang guard. Same expectations as T2.
- **T5, must not change:** a new folder with no restore still gets its database; a half-done restore (note present, no `clark.db`, flag not set) is still finished by the next start (existing tests keep passing, run unedited).
- **Mutants to try:** restore the old order in `finish_restore`; remove the second-layer check; clear the flag early; each must fail one of T1 to T4. Drop `mode=rw` from the open: T3, T7 and T8 must fail.

## 5. Two processes (a command-line restore against a running server)
`_UNDER_WAY` is a plain set in one process, so a second process never sees it. `python3 -m clark restore NAME` (`__main__.py:282`) runs `restore_path` in its own process; the server's request threads run `open_store` in another. The CLI is meant to be run with clark stopped (it prints "Start clark again to use it"), but **nothing enforces that**: the only check is `in_use`, and the server keeps no connection open between requests (#111), so it is usually idle and passes.

What protects what across processes:
- **The note file** (`clark.db.restoring.json`) is on disk, so both processes see it, but it is written late (see section 1), and in the server it makes `finish_restore` *finish* the restore, not wait for it.
- **SQLite locking** protects only a connection that is open. The CLI's `in_use` probe holds an exclusive lock on the old file until the move is done, so a server reader that connects before the move waits up to 5 seconds (`busy_timeout`) and then fails. Once `clark.db` has moved, the lock is on the moved file and a new reader sees no file, so SQLite makes an empty one: R1 again. WAL files are per file, so they move with it only if nobody has the old file open.

Failure sequences:
- **P1, server reads while the CLI swaps files.** The same as R1, with the flag invisible. The flag fixes do not close it (the flag is not set in the server process), but the no-create open in section 3 does, on every OS: a reader whose file has moved cannot make a new one, and `open_store` reports the existing words (or busy, if the lock below says a restore is running).
- **P2, the server finishes the CLI's restore.** The CLI has written the note and moved `clark.db`; a server reader calls `finish_restore`, finds the note, no `clark.db` and no flag, and takes the "stopped part-way" branch: it moves strays aside and replaces `clark.db` with the waiting copy, then removes the note. The CLI's own final replace then fails or overwrites, and the two disagree about which folder holds the old data.
- **P3, an idle connection across the swap.** A connection the server opened before the CLI started (only the Publisher's `publish()` keeps one) points at the old file in `replaced-*`; its writes are lost. Same as R3, and still out of scope here.
- **P4, two restores at once** (two terminals, or a terminal and Settings): both write the same note and `.restoring` copy.

The flag test and the second layer help only when restorer and reader share a process (the Settings restore, which is the server's own). The no-create open closes P1 across processes. P2 and P4 stay open without the lock, and P3 is unchanged.

**Smallest guard, recommended (new, small):** one lock file beside the database, `clark.db.restore.lock`, taken with the operating system's file lock (`fcntl.flock` on macOS and Linux, not `lockf`: `flock` locks are held per open file, so a second try in the same process is refused and the Settings restore's own threads are guarded, while `lockf` locks belong to the process and would let them through; absent on Windows, see below), which is released by itself if the process dies.
1. `restore_path` takes it exclusively without waiting, for its whole run, and takes it **before** it writes the `.restoring` copy (or the note), so two restores at once (P4) cannot both start. If it cannot: "This data is in use by another restore or another running copy of the program, so the restore did not start. Close the other one and try again. Nothing was changed." (A reader's momentary shared test can make the try fail by chance; the restorer retries for up to one second before it refuses, so the sentence is true when shown.)
2. `restoring(path)` (the helper in fix 2) answers true if the flag is set **or** the lock cannot be taken shared without waiting. `finish_restore` and `open_store` use it, so a server reader in another process meets the same `RESTORE_BUSY`, and P2 cannot happen because a lock holder is never "finished" by someone else.
**Who makes and removes the file.** `restore_path` creates `clark.db.restore.lock` if it is missing and never removes it: deleting a file another process holds locked would let a second restorer lock a new file of the same name. A reader never creates it (the folder may be read-only, or a first run); if the file does not exist, the reader treats it as not locked. The file is empty and harmless to leave. **Windows:** `fcntl` is not there, so on Windows this guard is absent unless a Windows call is added. Then the command-line restore against a running server keeps only P2 and P4 open (P1 is closed by the no-create open), and nobody is told; only the Settings restore is protected, by the flag. The note and the CLI help should say so.
The lock is never held across a request, so it cannot block normal use; a crash cannot leave it stuck. It touches `backup.py` (about 25 lines, the same file) and `platform.py` only if the Windows call is added there; no other file. Nothing is deleted and no database file is opened by the guard.
Smaller alternative: the CLI checks the port and refuses while a server answers. It needs no lock, but it misses a server on another port, and a server started during the restore.

**Test T6 (two processes, fails on today's code):** start a second Python process that takes the lock (or runs `restore_path` with a hook that waits on a file), then in the test process call `open_store` and `finish_restore`: expect `RESTORE_BUSY`, no empty `clark.db` made, and the second process's restore finishing with the old database whole in `replaced-*`. Plus T6b: two `restore_path` calls from two processes, the second is refused with the sentence above and changes nothing. Mutants: take the lock shared instead of exclusive (T6b must fail); use `lockf` instead of `flock` (a threaded test in one process must fail, because the second try is granted).

## 8. Open questions (with a recommendation)
1. **Should every read wait for the whole restore, including the long copy?** Recommend yes: honest, simple, and the only way a check made before the note can be trusted.
2. **Publisher across a restore (R3, P3): fix here or separately?** Recommend separately: it needs the restore and a publish to share one lock in the server, a different file set and its own test. Raise it as its own item now.
3. **Add a shared gate so the single-process stall cannot happen?** Recommend no: the no-create open already stops a stalled reader making or building anything.
4. **Add the lock file so a command-line restore is safe against a running server (section 5)?** Recommend yes, in the same change: without it the fix is correct only for the Settings restore, and the command-line one (the documented way to recover when the server will not start) stays open to P1, P2 and P4. If the owner declines, state in the CLI help and in the note that clark must be stopped first, since nothing enforces it.
